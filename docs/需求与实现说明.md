# TestWorkshop 车间测试管理平台 需求与实现说明

## 0. 总览

**业务背景**：船用液压产品的车间测试。下位机（测试台）产生测试数据，平台负责设备与订单管理、遥测数据归集、阈值与报警管理，并把报警以站内消息推给人。

**技术栈**：后端 ABP Framework 9.3.5 / .NET 9 / EF Core / PostgreSQL + TimescaleDB / Redis / SignalR；前端 Vue 3 + Vben5 + Ant Design Vue。

**关键角色**：

| 角色 | 标识 | 说明 |
| --- | --- | --- |
| 管理员 | admin | 全局，可看全部数据 |
| 车间主管 | supervisor | 隶属某个车间 |
| 测试工程师 | tester | 隶属某个车间，报警第一处理人 |
| 大区负责人 | regionalManager | 隶属某个车间 |
| 调度 | dispatcher | 全局岗位，不隶属车间，负责订单 |
| 单船项目主管 | projectSupervisor | 全局岗位，是订单上的必选人员 |
| 质量审核员 | auditor | 全局岗位 |
| 访客 | guest | 只读 |

**通用可见性规则**：设备和订单默认按用户所属组织单元（车间）过滤；`admin` 不受此限制。报警不再按人员或车间限制，所有登录用户都可以看到全部报警。

设备和订单模块共用组织单元可见性实现；订单模块有两条额外放开：

- **调度**：全局岗位、不隶属车间，但需要跨车间管理订单 → 订单可见范围里 `admin`、`dispatcher`、`auditor` 都视为不受限。
- **单船项目主管**：全局岗位、不隶属车间，但订单上有"单船项目主管"字段 → **可看自己负责的订单**（按订单上的 `ProjectSupervisorUserId` 判断）。

**各模块可见范围一览**：

| 模块 | admin | dispatcher（调度） | 车间角色（车间主管 / 测试工程师 / 大区负责人） | 单船项目主管 | 其他全局岗位（质量审核员 / 访客） |
| --- | --- | --- | --- | --- | --- |
| 设备管理 | 全部 | 无（不隶属车间） | 仅本车间 | 无 | 无 |
| 订单管理 | 全部 | **全部** | 仅本车间 | **自己负责的订单** | 质量审核员：全部 |
| 报警管理 | **全部** | **全部** | **全部** | **全部** | **全部** |

> 说明：调度和单船项目主管在设备管理里没有豁免，因为设备数据按车间归属。报警管理是全员可见的报警列表，不再按角色和车间过滤。

**通用时间口径**：下位机上报的都是**本地时间**（东八区）。入库统一按 UTC 存储；平台内部与"当前时间"比较时使用本地时间，口径一致。

**通用状态与枚举**：

- 设备类型 `DeviceTypeEnum`：FIVA=1、PUMP=2、ICU=3、SENSOR=4
- 报警类型 `WorkshopAlarmType`：阈值=1、关联=2、设备=3、通信=4
- 报警状态 `WorkshopAlarmStatus`：进行中=1、已恢复=2
- 订单状态 `WorkshopOrderStatus`：Draft=0（已录入未测试）、Testing=1、PendingReview=2（测试完成未审核）、Cancelled=3、ReviewApproved=4、ReviewRejected=5
- 测试报告状态 `WorkshopTestReportStatus`：NotReady=0、Fetching=1、Ready=2、Failed=3
- 遥测任务状态：Pending=0、Processing=1、Success=2、Failed=3

## 1. 组织单元（车间）

- 车间的载体是 ABP 的**组织单元 `OrganizationUnit`**，通过扩展属性 `BusinessCode` 存车间业务编码（种子数据：黄岛车间 `HD`、宁波车间 `NB`、深圳车间 `SZ`）。
- 组织树：公司（青岛儒海船舶股份有限公司）→ 黄岛车间 / 宁波车间 / 深圳车间。
- 每个车间下挂三类账号：`{前缀}.supervisor`（车间主管）、`{前缀}.regional`（大区负责人）、`{前缀}.tester`（测试工程师）。新增子机构时可勾选“初始化车间人员”，新车间挂到当前选中的组织单元下，账号前缀取 `BusinessCode` 的小写形式；种子数据显式传入固定 ID 和公司组织单元 ID，两条路径共用同一个开通服务，已有账号、角色和组织归属不会重复创建。
- 全局岗位（不隶属车间）：调度、单船项目主管、质量审核员。
- 车间是**设备和订单的数据权限边界**。报警列表不按车间过滤，所有登录用户可见。

## 2. 设备管理

**实体 `WorkshopDevice`（表 `AppWorkshopDevices`）**

| 字段 | 说明 |
| --- | --- |
| `Code` | 设备编码，下位机上报用，如 `HD-FIVA-001` |
| `Name` | 设备名称，如 "FIVA测试台" |
| `Type` | 设备类型（FIVA / PUMP / ICU / SENSOR） |
| `OrganizationUnitId` | 所属车间 |
| `TenantId` | 租户（当前不使用） |

约束：`(TenantId, Code)` 唯一。

**业务规则**

1. 设备编码创建后不可修改；重复编码报错。
2. 列表按当前用户可访问车间过滤；可按编码/名称模糊查、按类型筛、按车间树节点筛（选中车间时包含其下级车间）。
3. 新增 / 编辑 / 删除**仅管理员**可操作；非管理员操作用户范围外的车间会报"无权操作该车间的设备"。
4. 设备类型选项由接口返回（值 + 名称 + 本地化显示名）。

**接口**

- `GET /api/workshop/device`（分页，含 filter/type/organizationUnitId）
- `GET /api/workshop/device/{id}`
- `POST /api/workshop/device`、`PUT /api/workshop/device/{id}`、`DELETE /api/workshop/device/{id}`
- `GET /api/workshop/device/organization-units`（当前用户可见的组织单元树）
- `GET /api/workshop/device/types`（设备类型选项）

**菜单**：业务管理 → 车间设备（所有角色可见，数据按车间过滤）。

## 3. 订单管理

**实体 `WorkshopOrder`（表 `AppWorkshopOrders`）**

| 字段 | 说明 |
| --- | --- |
| `OrderNo` | 订单号（唯一，按租户过滤） |
| `DeviceId` | 关联设备（测试台），一单一设备 |
| `Status` | Draft / Testing / PendingReview / Cancelled / ReviewApproved / ReviewRejected |
| `TestStartedAt` / `TestEndedAt` | 实际测试开始/结束时间（本地时间） |
| `ProjectSupervisorUserId` | 单船项目主管 |
| `RequiredCompletionTime` | 要求车间完成测试时间 |
| `TestReportStatus` | 测试报告获取状态；具体文件通过 `FileObject.OwnerType=WorkshopTestReport`、`OwnerId=订单ID` 查询 |
| `TestReportFetchedAt` / `TestReportError` | 测试报告获取完成时间、失败原因 |

**业务规则**

1. **一个订单关联一台设备；同一台设备同时只能有一个"测试中"的订单**（数据库部分唯一索引 `DeviceId WHERE Status = 1` 保证）。
2. 状态流转：
   - 只有 `Draft`（已录入）可以修改；
   - `开始测试`：Draft → Testing，并占用设备；
   - `结束测试`：Testing → PendingReview；
   - `取消订单`：Draft/Testing → Cancelled（测试完成或进入审核后不可取消）；测试中取消会记录结束时间。
   - `审核`：PendingReview/ReviewRejected → ReviewApproved/ReviewRejected；审核不通过允许再次审核，审核通过后锁定。
   - 只有 `TestReportStatus=Ready` 且报告文件存在时才能审核；只有 `ReviewApproved` 才能下载最终报告。
3. 时间校验：结束时间不能早于开始时间；开始/结束时间不能为空。
4. **可见性**：`admin` + `dispatcher` + `auditor` 可看**全部**订单；**单船项目主管可看自己负责的订单**（按订单上的 `ProjectSupervisorUserId`）；其他角色只看**自己所属车间设备**的订单。不仅列表过滤，按 id 访问的入口（订单详情、开始/结束/取消测试、审核记录、订单下遥测任务列表、遥测图谱）都做同样的校验，避免绕过列表直接访问。
5. **操作权限**：新建/编辑/删除 = 管理员 + 调度；开始/结束测试 = 管理员 + 车间主管 + 测试工程师；取消订单 = 管理员 + 车间主管 + 测试工程师。
6. **订单创建通知**：订单创建后给"设备所属车间"的车间主管与大区负责人发站内消息，标题带订单号，内容包含设备、要求完成时间。
7. **审核记录**：每次审核追加一条记录，保存审核人、审核时间、通过/不通过、维保建议和当时的报告文件数量，不覆盖历史记录。
8. **报告查看与下载**：`admin`、`auditor` 在审核前可在线预览报告；`admin`、`auditor`、`dispatcher` 可下载全部已审核通过的报告；`projectSupervisor` 只能下载自己负责订单的报告。未审核通过或报告未就绪时，前后端都禁止下载最终报告。
9. **报告轮询**：本轮只预留报告状态、文件字段和获取失败原因，外部接口轮询暂不实现。
10. **多文件报告与预览**：原始报告文件通过 `FileObject.OwnerType=WorkshopTestReport`、`OwnerId=订单ID` 关联，一份订单允许多个文件。预览接口直接返回用户选择的原始文件供浏览器显示，不额外保存预览文件；订单列表显示“测试报告”列和文件数量，点击后打开文件列表并切换预览。原始文件批量下载仍受审核状态和角色限制。
11. **多文件下载**：审核通过后，“下载报告”会把该订单的全部原始报告文件打包成一个 ZIP 下载，文件名格式为 `订单号-测试报告.zip`。

**接口**

- `GET /api/workshop/orders`（分页，订单号/设备/状态/时间范围筛选）
- `GET /api/workshop/orders/{id}`
- `POST /api/workshop/orders`、`PUT /api/workshop/orders/{id}`、`DELETE /api/workshop/orders/{id}`
- `POST /api/workshop/orders/{id}/start`、`/{id}/end`、`/{id}/cancel`
- `POST /api/workshop/orders/{id}/audits`、`GET /api/workshop/orders/{id}/audits`
- `GET /api/workshop/orders/{id}/test-report/download`
- `GET /api/workshop/orders/{id}/test-report/preview`（首个报告文件，全部登录用户可用）
- `GET /api/workshop/orders/{id}/test-report-files`（全部登录用户可查看报告文件列表，返回预览 key）
- `GET /api/workshop/orders/{id}/test-report-files/{fileKey}/preview`（全部登录用户可预览所选原始文件）
- `GET /api/workshop/orders/{id}/telemetry-tasks`、`GET /api/workshop/orders/{id}/telemetry-graph`
- `GET /api/workshop/orders/project-supervisors`（单船项目主管选项）

**菜单**：业务管理 → 订单管理。

## 4. 阈值管理

**物理量定义（代码常量，固定 5 个）**

| 编码 | 名称 | 单位 |
| --- | --- | --- |
| `Pressure` | 压力 | MPa |
| `Flow` | 流量 | L/min |
| `Temperature` | 温度 | ℃ |
| `Torque` | 扭矩 | N·m |
| `Vibration` | 振动 | mm/s |

物理量是平台内部标识，时序宽表列、阈值规则、报警判定统一使用它；下位机上报的字符串在数据入口归一化（编码任意大小写、中文名都认），认不出记日志忽略。单位不落库，由常量提供。

**实体 `WorkshopThresholdRule`（表 `AppWorkshopThresholdRules`）**

| 字段 | 说明 |
| --- | --- |
| `DeviceType` | 设备类型（**按测试台类型配置，同一型号共用一套**） |
| `DataItemType` | 物理量编码 |
| `UpperLimit` | 上限阈值，可空（超过视为偏高） |
| `LowerLimit` | 下限阈值，可空（低于视为偏低） |
| `AlarmContent` | 报警内容（人工填写的说明，如"压力偏高"） |
| `Enabled` | 是否启用 |

约束：`(DeviceType, DataItemType)` 唯一（仅对未删除行生效）。

**业务规则**

1. 按**设备类型**配置，不按单台设备。
2. 上限/下限至少填一个；下限不能大于上限。
3. **两个都留空 = 该数据类型不设阈值**（保存时删除已有规则），不报错。
4. 一个物理量如果一个方向不需要监控，留空即可。

**接口**：`GET /api/workshop/threshold/{deviceType}`（固定返回 5 个数据类型，未配置的为空）、`POST /api/workshop/threshold/save`（按设备类型整批保存，仅管理员）。

**页面**：平台管理 → 阈值管理（**仅管理员可见/可写**）。顶部选设备类型，下面 5 行（压力/流量/温度/扭矩/振动）填上下限、报警内容、启用。

## 5. 遥测数据（两类，注意区分）

### 5.1 图谱数据（属于"被测设备"，走文件上传）

- 下位机上传 CSV（内容只有 `index,value`，index 从 0 连续递增，单文件上限 100 万采样点）+ 一批参数（`DeviceCode`、`ChannelType`、`FileTime`、`TestInfo.StartTime/EndTime/StartTime2/EndTime2/TestDate`、被测设备信息、船名、测试人等）。参数扁平化写入 `FileObject.ExtraProperties`（前缀 `TelemetryInput.`）。
- 平台创建遥测任务 `WorkshopTelemetryTask`（状态 Pending→Processing→Success/Failed，含重试次数与下次重试时间），后台 worker 认领并解析，写入 **TimescaleDB 超级表 `AppWorkshopDeviceTelemetries`**。
- 表主键 `(DeviceId, Timestamp, ChannelType)`；`Value` 为 `double precision[]` 波形数组；`Timestamp` 来自 `FileTime`，是超级表时间分区列。
- **订单归属**：按订单的实际测试开始/结束时间匹配（可配容差，默认 0）；没有归属到订单的数据标记为“未关联订单”。
- 保留：任务与原始文件按 `WorkshopTelemetry:RetentionDays`（当前 1095 天）到期清理，由清理 worker 执行；清理任务**不删除**超级表数据，超级表需单独制定归档/清理策略。实时数据的保留期与压缩策略见"其他"模块第 1 项。

### 5.2 实时数据（属于"测试台"，走下位机推送）

- 一行 = 一台测试台一次推送，**多个物理量是同一行的多列**（与图谱数据不同，这里没有"被测设备"信息）。
- 表 `AppWorkshopRealtimeData`（TimescaleDB 超级表，主键 `(DeviceId, Timestamp)`）。

| 字段 | 说明 |
| --- | --- |
| `DeviceId` / `DeviceCode` | 测试台 |
| `Timestamp` | 采集时间（下位机给，本地时间，转 UTC 存），分区列 |
| `Pressure` / `Flow` / `Temperature` / `Torque` / `Vibration` | `numeric(18,4)`，**可空**（采集不到的为空） |
| `EmergencyStop` | 测试台急停，`true` = 急停 |
| `ReceivedAt` | 服务器接收时间（平台自己记，不由下位机传） |

- **接收接口**：`POST /api/workshop/realtime-data`（下位机调用，匿名暴露，受访问密钥保护，见 5.3）

```json
{
  "deviceCode": "HD-FIVA-001",
  "timestamp": "2026-10-14T10:52:27",
  "values": { "Pressure": 12.5, "Flow": 30 },
  "emergencyStop": false
}
```

  规则：`timestamp` 是本地时间（不带时区按服务器本地时间处理）；`values` 是物理量键值对，键大小写不敏感、也认中文名，认不出的记日志忽略、不影响同帧其它量；采集不到的不传；同一 `(设备, 时间)` 重复推送**覆盖**；设备编码必须已登记，否则返回"未知设备编码"。
- 实时数据是**阈值报警**与**设备报警**判定的输入（判定规则见第 6 节）；实时数据的页面展示方案（页面载体、展示维度、刷新或推送频率）见"其他"模块第 2 项。

### 5.3 下位机接口的访问密钥（已实现，默认关闭）

下位机调用的三个接口在下位机侧没有登录态，只能匿名暴露，因此加了一层共享密钥校验：

| 接口 | 用途 |
| --- | --- |
| `GET /api/workshop/telemetry/online?deviceCode={设备编码}` | 心跳登记，并返回服务器时间供下位机校时；按设备编码 upsert 一行“最新心跳时间”，不会持续增长（见第 8 节的心跳监控 Worker） |
| `POST /api/workshop/telemetry/upload` | 上传 CSV 图谱数据（见 5.1） |
| `POST /api/workshop/realtime-data` | 推送一帧实时数据（见 5.2） |

- 下位机在请求头带 `X-Device-Key: {密钥}`。密钥**缺失或错误时直接返回 401**（空 body），请求不会进入业务逻辑；服务端会记一条 warning 日志（含请求方法与来源 IP），便于排查是谁在拿错密钥。
- 开关与密钥放在配置里：`DeviceApi:Enabled`、`DeviceApi:ApiKey`；生产环境建议用环境变量 `DeviceApi__ApiKey` 覆盖，不要写进 appsettings。
- **当前状态：`Enabled` = false，尚未开启**，三个接口仍可匿名访问。等所有下位机都加上请求头之后再打开。
- 开启顺序：先把 `Enabled` 置为 false 部署服务端（版本就位但不校验）→ 下位机逐个加上请求头 → 再把 `Enabled` 改为 true 重新部署。若在开启状态下直接部署，未带请求头的下位机会全部 401，心跳中断还会连带触发通信报警。
- 设备端建议把 **401 单独识别**为“密钥错误”，而不是当作普通业务错误去重试。
- 维护提示：以后新增下位机接口时，需要同步加入中间件的受保护路径列表，否则不会走密钥校验。
- **运行总时长**：设备心跳表保存首次心跳时间、最后心跳时间和累计运行秒数。每次收到心跳时，如果与上一次心跳间隔不超过 `WorkshopAlarm:RuntimeGapToleranceSeconds`（当前 6 秒），就把该间隔计入运行总时长；超过该窗口的断线时间不计入。设备列表展示最后心跳时间和累计运行时长。

## 6. 报警管理

### 6.1 报警分类（4 大类）

| 类型 | 判定依据 |
| --- | --- |
| 阈值报警 | 实时值超出该设备类型、该物理量配置的阈值上下限 |
| 关联报警 | 跨参数：由换算公式给出"正常范围"，判断实际物理量是否在范围内（**公式待需求方提供，暂未实现**） |
| 设备报警 | **传感器类型设备**的读数超阈值上下限（即"传感器故障"，只对 `SENSOR` 类型判定）；测试台急停（任意设备类型） |
| 通信报警 | 心跳间隔超过超时阈值（当前 10 秒） |

### 6.2 报警状态表 `AppWorkshopAlarms`

| 字段 | 说明 |
| --- | --- |
| `AlarmType` | 报警类型 |
| `DeviceId` / `DeviceCode` | 报警主体是**测试台** |
| `OrganizationUnitId` | 测试台所属车间，仅作为设备归属信息，不再过滤报警可见性 |
| `DataItemType` | 物理量编码；通信报警为空字符串（不区分物理量） |
| `Content` | 报警内容 |
| `StartedAt` | 报警成立时间 |
| `Status` / `ClearedAt` | 进行中/已恢复、恢复时间 |

唯一性：`(AlarmType, DeviceId, DataItemType)` **同时只允许一条进行中的报警**（数据库部分唯一索引保证）。

### 6.3 报警的成立与恢复

1. **检测周期**：阈值报警、设备报警和通信报警的扫描周期统一为 10 秒。
2. **即时成立**：判定 Worker 取每台设备最新一帧数据；当前值超限时立即创建“进行中”报警，不等待持续时长。检测延迟取决于下一次轮询，最大约 10 秒。
3. **不再通知人员**：取消 5/10/20 分钟升级、收件人计算、站内消息和通知级别字段。报警只进入报警列表。
4. **正常恢复**：后续最新数据回到正常范围时，报警置为“已恢复”并记录恢复时间。
5. **数据停发不自动恢复**：设备停止上报后，已有数据类报警保持“进行中”，不会因为长时间没有新数据而自动关闭；只有后续收到正常数据时才恢复，收到异常数据则继续保持。
6. **通信报警**：设备最后一次心跳距当前超过 `WorkshopAlarm:CommunicationTimeoutSeconds`（当前 10 秒）时产生“通信中断”报警；心跳恢复后关闭报警。轮询周期为 10 秒，因此实际发现时间约为 10～20 秒。
7. **报警主体**：阈值报警、设备报警和通信报警都按测试台设备维度生成；急停仍产生“测试台急停”设备报警。
8. **列表刷新**：报警页面每 10 秒自动刷新一次，所有登录用户看到的是同一份全量报警列表。
### 6.4 可见性与权限

- 报警列表不再按车间、角色、人员或组织单元过滤。
- 所有登录用户看到同一份全量报警数据。
- 报警不再通过站内消息通知任何人。

- 页面：业务管理 → 报警管理（进行中/已恢复，每 10 秒自动刷新）

## 7. 消息与通告

- **站内消息**用于订单通知和人工消息，不再承载报警通知；每人一行（可已读/未读），通过 SignalR 实时推送。
- 消息有**类型**（普通/广播）和**级别**（警告/普通/错误）。
- 平台管理 → 消息管理：可按标题、内容、级别、已读状态、**接收人**筛选；支持设为已读、批量已读、删除、发送消息（发送人记当前登录用户）。
- 平台管理 → 通告管理：广播消息的发送与管理。
- 业务管理 → 我的消息 / 我的通告：当前用户自己的消息与通告（消息在前、通告在后）。

**已读状态的口径（与代码一致，2026-10-16 核查）：**

- 普通消息：一条消息 × 一个收件人 = 一行记录（`ReceiveUserId` / `Read` / `ReadTime`），发给 3 个人就是 3 行，所以能查到"哪个收件人已读"。
- 通告（广播）：消息只存一行，已读按人记录在订阅表（`NotificationId + ReceiveUserId + Read + ReadTime`），且**只有读过的人才有记录**；没读的人没有行，"未读"只能按"没有记录"推断。
- **当前不记录"是谁点的已读"**：标记已读的接口只按消息 id 更新收件人那一行的状态，不校验操作人是否就是收件人，也不写操作人字段。管理员在"消息管理"里点"设为已读 / 批量已读"，库里看起来就是收件人本人已读。
- 目前没有"某条通告谁已读 / 谁未读"的名单：订阅列表接口只返回当前登录用户自己的状态，平台侧"通告管理"页面只有发送、查询和删除。

## 9. 关键业务约定速查

1. **车间是设备和订单的数据权限边界**。报警列表所有登录用户可见全部数据。
2. **报警主体是测试台**，不是被测设备。
3. **两类遥测数据不能混**：图谱数据是被测设备的（文件上传），实时数据是测试台的（接口推送）。
4. **时间是本地时间**，只有时间戳字段统一转 UTC 存储。
5. **报警不发送人员通知**，只维护报警列表状态。
6. **报警检测每 10 秒一次，异常即成立**；数据停发不自动关闭报警。
7. **物理量固定 5 个**，用字符串编码，下位机字符串在入口归一化。

### 10.1 报告管理（已实现订单审核链路，轮询暂缓）

外部系统按订单号提供订单报告（**一单一报告**，对方审核完成后不可修改），平台定时轮询获取、审核通过后可下载。

**当前实现：** 报告管理收进订单模块。订单保留报告状态和最近成功获取时间，外部请求过程通过 `AppWorkshopOrderReportFetchRecords` 记录；一份订单支持多个报告文件，订单列表显示文件数量，所有登录用户可以打开文件列表并切换预览。质量审核员可查看全部订单并审核、下载最终报告；管理员、调度员可下载全部已审核报告；单船项目主管只能下载自己负责订单的报告。审核不通过可再次审核，审核通过后锁定状态并开放下载。
